# Scientific Cartography Map UX v0.2b — Static Prototype Spec
Date: 2026-06-23

---

## 1. Objective

Produce a static, file://-openable HTML+SVG disease landscape map for **type 2 diabetes mellitus** (MONDO:0005148) that communicates competitive structure, mechanism coverage, and data-quality state to an investment analyst without requiring a server, framework, or live data connection. The map is a diagnostic visualization only — its purpose is to make the shape of the T2DM competitive landscape legible and to surface where the current data pipeline is blind (stage, mechanism). Output is a self-contained directory of four files generated by a single Python script that reads existing diagnostic artifacts. No portfolio signals, no scoring integration, no production wiring.

**Selected disease: type 2 diabetes mellitus (MONDO:0005148)**

Evidence from the 2026-06-23 diagnostic run:

- **Program count:** 1,046 — 6th-largest disease in the index; materially smaller than lymphoma (5,495) and breast cancer (2,340) but large enough to be representative
- **Ticker count:** 53 public tickers — broad universe coverage; non-oncology disease, so program-per-ticker ratio is lower and asset identities are more distinct
- **Cluster count:** 3 competitive clusters in MONDO:0005148. Two have real mechanism data (GLP-1 receptor agonist / small molecule / GLP1R; TNF inhibitor / monoclonal antibody / TNF). The third cluster groups the 1,041 mechanism-unknown programs.
- **Known mechanism count:** 5 programs with known mechanism (out of 1,046 = 0.48%); highest non-oncology count in the disease index after lymphoma (13)
- **Source refs count:** 513 distinct ClinicalTrials.gov NCT IDs — strong source anchoring for the 200-program `Diabetes Mellitus, Type 2` sub-entity; 1,046 total features across 513 refs

**Stage data state:** 100% unknown for all 1,046 T2DM programs. This is a system-wide issue (field name mismatch: `phase` vs `phases`, `status` vs `overall_status` in `_parse_simplified_format` in `ctgov_ingest.py`). The prototype must surface this prominently and use a fallback column scheme. The reader must not be misled into thinking stage data exists.

## 5. Visual Grammar

### Map frame

The map is organized as a **two-axis grid**:

- **Rows (Y-axis / lanes):** Mechanism classes. One lane per distinct mechanism class found in the competitive clusters, ordered by program count descending. An additional final lane labeled **"[mechanism unknown]"** holds all programs where `mechanism_class` is null.
- **Columns (X-axis):** Stage is 100% unknown, so the fallback column scheme uses **source-ref count** as a proxy for evidence depth. Programs are binned into three columns:
  - **"Single source"** — `source_refs_count == 1`
  - **"Multi-source (2–9)"** — `source_refs_count` between 2 and 9
  - **"Deep evidence (10+)"** — `source_refs_count >= 10`
  
  Each column is labeled with its bin definition. A prominent banner above the map reads: **"Stage data unresolved — columns show source-ref depth, not clinical stage. See Implementation Notes."** The column headers are rendered in amber to signal the fallback state, not the intended design.

### Node encoding

Each node represents one program (one row in `landscape_features.jsonl` for the target disease).

| Visual property | Encoding |
|---|---|
| **Shape** | Circle for all nodes in this prototype. Modality distinction is deferred until mechanism normalizer coverage improves. |
| **Size** | Fixed radius for all individual program nodes. Cluster summary nodes (one per cluster in the mechanism legend) are larger (2× radius). |
| **Fill color** | Mechanism class drives hue: GLP-1 receptor agonist → blue-green; TNF inhibitor → amber-orange; unknown mechanism → slate-grey at 40% opacity. If future mechanism classes are present, assign from a fixed 6-color categorical palette, reserving grey for unknown. |
| **Stroke** | Source-ref count drives stroke weight: 1 source → hairline (0.5px); 2–9 → medium (1.5px); 10+ → heavy (2.5px). Stroke color matches fill at higher saturation. |
| **Opacity** | `feature_confidence == 0.0` → base opacity 0.55. When confidence > 0 (future state), opacity 0.9. This visually distinguishes the current all-zero confidence state from future improved data. |

### Label rules

- **Cluster lane labels (row axis):** Mechanism class name, left-aligned, uppercase small caps, with program count in parentheses. Example: `GLP-1 RECEPTOR AGONIST (5)` / `[MECHANISM UNKNOWN] (1,041)`.
- **Column headers:** Source-ref bin label, centered, with the amber warning treatment when stage is unresolved.
- **Individual program node labels:** Ticker symbol only, rendered at 8px below each node, clipped if overlapping. Only render ticker label if the program's ticker appears in the screener universe (`public_tickers` from the cluster record). Non-universe tickers are unlabeled.
- **Cluster summary callout:** For each named-mechanism cluster, render the asset names as a small tooltip-style text block anchored to the cluster's centroid. Include only the first three asset names, followed by "+ N more" if count exceeds three.

### Tooltip / sidecard content

On hover/focus of a program node, reveal a sidecard panel (absolutely positioned, stays within viewport). Sidecard fields:

- Asset name
- Ticker (if universe member: bold; otherwise normal weight)
- Mechanism class (or "[unknown]")
- Modality (or "[unknown]")
- Source refs: first three NCT IDs as links formatted as `NCT#######` (non-clickable in file:// context; rendered as monospace)
- Source ref count: "N ClinicalTrials.gov records"
- Feature confidence: rendered as a fraction-bar — e.g., "Confidence: 0.00" with a note "Low confidence — mechanism/stage data absent"
- Warnings list from the feature record (comma-separated, rendered in amber)

### Unknown-state rendering

Three distinct visual treatments for unknown/absent data:

1. **Stage unknown (system-wide):** Column axis replaced with source-ref proxy. Column headers rendered in amber with a warning icon (⚠). A non-dismissible banner appears above the map.
2. **Mechanism unknown (per-node):** Grey fill at 40% opacity. The `[mechanism unknown]` lane is visually separated from named-mechanism lanes by a 2px dashed row divider. Lane background is light grey, distinct from white named-mechanism lane backgrounds.
3. **Confidence zero (per-node):** Reduced node opacity (0.55). A legend entry reads: "Faded nodes = zero confidence (mechanism/stage data absent)".

## 6. Data Pipeline (no server)

The generator script `tools/generate_scientific_cartography_map_ux.py` runs as a standalone CLI and produces the four output files. No server process, no live data access, no network calls.

**Step 1 — Load inputs**

Read from `artifacts/scientific_cartography/{as_of_date}/`:
- Parse `map_index.json` → extract the entry for `disease_id == "MONDO:0005148"` → yields disease-level metadata (program_count, tickers, cluster_count, known_mechanism_count, source_refs_count, stage_distribution)
- Stream `competitive_clusters.jsonl` → filter rows where `disease_id == "MONDO:0005148"` → yields 3 cluster records
- Stream `landscape_features.jsonl` → filter rows where `disease_id == "MONDO:0005148"` → yields 1,046 feature records
- Read `artifact_manifest.json` → yields governance block and input provenance
- Read `scientific_cartography_status.json` → yields run status and warnings

**Step 2 — Build the map data model**

Construct the `MapData` structure (defined in Section 7):

- `disease`: populated from map_index entry
- `stage_resolved`: set `false` (confirmed: all stage values are 0)
- `column_scheme`: set `"source_ref_depth"` since `stage_resolved == false`
- `columns`: build three column definitions from source_ref bins [1, 2-9, 10+]
- `mechanisms`: for each unique `mechanism_class` in cluster records (including null), create a `MechanismLane`. Sort: named mechanisms first by total `program_count` descending, then null/unknown lane last.
- `programs`: for each landscape_feature record, compute:
  - `source_ref_count` from `len(source_refs)` on the feature record
  - `column_bucket` from the source_ref_count bin
  - `is_universe_member` from whether `ticker` appears in the disease's `public_tickers` list
  - `display_label` = ticker if `is_universe_member`, else empty string
  - All other fields pass through directly from the feature record

**Step 3 — Layout algorithm**

The SVG layout is computed in Python before writing the SVG — no JavaScript layout, all coordinates are burned into the SVG.

- Define constants: `NODE_RADIUS = 7`, `NODE_MARGIN = 4`, `LANE_PADDING = 20`, `COLUMN_WIDTH = 240`, `LANE_LABEL_WIDTH = 220`, `HEADER_HEIGHT = 80`
- For each mechanism lane, collect all programs in that lane and sort them by source_ref_count descending
- Pack nodes within each lane×column cell using a simple row-wrap packing: place nodes left-to-right, wrap to next row when column width is reached
- Compute cell height from the packed node count in that cell; lane height = max cell height across all three columns + `LANE_PADDING`
- Assign each node an `(cx, cy)` coordinate in the SVG coordinate space
- Total SVG height = sum of lane heights + `HEADER_HEIGHT`. Total SVG width = `LANE_LABEL_WIDTH + 3 * COLUMN_WIDTH`
- Nodes for the mechanism-unknown lane are rendered identically but with grey fill and reduced opacity
- Write coordinates to each program record in the `MapData` structure (adds `svg_cx`, `svg_cy` fields)

**Step 4 — Render SVG**

Produce the SVG as a string using Python string formatting (no SVG library needed; output is simple circles, text, and lines):

- SVG root with `viewBox="0 0 {width} {height}"`, `width="100%"`, `height="{height}"`, `xmlns="http://www.w3.org/2000/svg"`
- Background rect for the full SVG
- Column headers (3 text elements at x = lane_label_width + col_index * col_width + col_width/2)
- For each mechanism lane: background rect (white or light-grey for unknown), left-edge lane label text, dashed separator line above unknown lane
- For each program node: `<circle>` with computed cx/cy/r/fill/stroke/opacity, `data-feature-id` attribute for JS hover binding, and a `<title>` child with the asset name (fallback tooltip)
- Ticker labels: `<text>` below each labeled node
- Source-ref depth legend in top-right corner (three circle examples at different stroke weights)
- Mechanism color legend in top-left (below column headers)

**Step 5 — Wrap in HTML**

Build `index.html` as a single string:

- `<title>T2DM Landscape Map — Scientific Cartography v0.2b (2026-06-23)</title>`
- Inline CSS: page layout, banner styles (amber for stage warning), sidecard panel (hidden by default), legend styles
- Inline the SVG string directly in the `<body>` (not via `<img>`) so that JavaScript can attach hover handlers to SVG elements
- Inline JavaScript: attach `mouseover`/`mouseout` listeners to all `<circle>` elements; on hover, populate sidecard from the `MAP_DATA` JS object (a JSON literal of the `programs` array written inline) and position the sidecard near the cursor; on mouseout, hide sidecard
- Data quality banner: always-visible amber strip at top of page stating "Stage data unresolved — columns reflect source-ref depth. See README.md for fix instructions."
- Footer: as_of_date, input artifact paths, governance attestation from `artifact_manifest.json`

**Step 6 — Write output files**

- Create output directory `artifacts/scientific_cartography/map_ux/type-2-diabetes-mellitus/` (parents OK)
- Write `map.json` from the `MapData` structure (JSON, pretty-printed, 2-space indent)
- Write `map.svg` (standalone SVG string)
- Write `index.html` (full HTML string)
- Write `README.md` (plain text / markdown summary)
- Print a brief summary to stderr: file paths written, node count, mechanism lane count, warnings

**CLI interface:**

```
python3 tools/generate_scientific_cartography_map_ux.py \
  --as-of-date 2026-06-23 \
  --input-dir artifacts/scientific_cartography/2026-06-23 \
  --output-dir artifacts/scientific_cartography/map_ux/type-2-diabetes-mellitus \
  --disease-id MONDO:0005148
```

All paths resolve relative to the repository root. `--disease-id` defaults to `MONDO:0005148`.

## 10. Implementation Notes

**Stage field name mismatch (blocking for future v0.2c):**
The `_parse_simplified_format` method in `scientific_cartography/ingest/ctgov_ingest.py` reads `data.get("phases", [])` and `data.get("overall_status")`. The `trial_records.json` file stores phase as a singular string `"phase"` (e.g., `"PHASE2"`) and status as `"status"`. This causes 100% null stage on all programs. The v0.2b prototype must render correctly with stage=null and must not defer generation until this is fixed; instead it uses the source-ref-depth fallback column scheme documented above.

**T2DM disease fragmentation:**
The disease normalizer has not fully consolidated all T2DM variants. `map_index.json` contains at least 11 distinct disease entries that are clinical variants of T2DM ("Diabetes Mellitus, Type 2", "Type 2 Diabetes (T2DM)", "Diabetes Type 2", etc.) in addition to the canonical MONDO:0005148 entry. The prototype uses only MONDO:0005148 (1,046 programs, 53 tickers). This means the displayed program count is not the total T2DM landscape; that caveat must appear in the map header and README.

**Cluster count discrepancy (3 MONDO clusters, not 1):**
`map_index.json` reports `cluster_count: 3` for MONDO:0005148. In `competitive_clusters.jsonl`, the 3 clusters are: GLP-1 RA (1 program), TNF inhibitor (4 programs), unknown (1,041 programs). The named-mechanism clusters are extremely small relative to the unknown bucket. The map must not imply that these 5 known-mechanism programs are representative of the mechanism distribution; the legend should note "mechanism resolution covers 5/1,046 programs (0.48%)".

**Node count and SVG performance:**
1,046 nodes is within SVG performance bounds for static rendering (~1–3k circles is typically fine in modern browsers without virtualization). If the unknown-mechanism lane causes visual crowding, the implementer may apply a sampling strategy: show all universe-member tickers (labeled nodes) and a random sample of N=100 non-universe nodes in the unknown lane, with a note "showing 100 of 1,041 mechanism-unknown programs". The sampling must be deterministic (seeded by `as_of_date` string hash). Labeled universe-member nodes are never sampled out.

**Mechanism color palette:**
With only 2 named mechanisms and 1 unknown, the color palette is simple. Recommended: GLP-1 RA → `#2D8B72` (teal-green, associating with GLP-1's metabolic/incretin class); TNF inhibitor → `#C97A35` (amber-orange, associating with inflammatory pathway); unknown → `#8A96A3` (neutral slate-grey). Reserve `#2D6A9F`, `#7B52A8`, `#A84D4D`, `#4A8A6F` for future mechanism classes.

**Hover implementation note:**
The `MAP_DATA` inline JSON object in `index.html` should be indexed by `feature_id` for O(1) hover lookup. Build a JavaScript object literal `{ "feature_id_1": {...}, "feature_id_2": {...} }` rather than an array, since the hover handler receives the `data-feature-id` attribute value directly.

**File:// compatibility:**
Do not use `fetch()` in the hover handler — CSP and file:// protocol both block it. All program data must be written inline in the HTML as a JS object literal. The sidecard must be a pre-existing hidden DOM element that gets populated, not dynamically inserted, to avoid innerHTML injection risks.

**map.svg as standalone file:**
The SVG written to `map.svg` must be a complete, valid SVG document with an XML declaration and `xmlns` attribute. The version inlined in `index.html` omits the XML declaration (browsers don't need it in inline SVG context) but is otherwise identical.
