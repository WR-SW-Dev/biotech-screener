## What happened

The 2026-07-27 daily production run was missed (WSL host down through Monday's
16:30 ET cron window). The catch-up scanner detected the gap on first boot and ran
the backfill on 2026-07-28 08:05:59–08:31:38 EDT. The snapshot itself is sound.

While that run was in flight, the checkout's HEAD was moved:

**Cause:** operator-side (this session), not a pipeline defect. The gate behaved
exactly as designed. `tools/run_forward_validation.py` receives the wrapper's HEAD via
`--expect-commit` and compares it to the snapshot manifest's `commit_sha`; moving HEAD
between run start and step [6] guarantees a mismatch.

## Why it is not recoverable

`tools/run_forward_validation.py:756-766`:

```python
capture_mode = args.capture_mode
if capture_mode == "LIVE" and (freshness_failures or args.force):
    # downgrading capture_mode LIVE -> REPLAY (freshness gate bypassed or --force)
    capture_mode = "REPLAY"
...
eligible_at_capture = capture_mode == "LIVE" and quality == "PASS" and model_hash_match and benchmark_available
```

`--force` unconditionally downgrades the capture to `REPLAY`, and `REPLAY` windows are
by construction `eligible_for_mandate: False` (`capture_is_eligible_for_mandate`,
line 251ff., requires `capture_mode == "LIVE"`). Therefore a forced backfill would:

- add a `REPLAY` row that inflates the **descriptive** all-windows statistics, and
- contribute **zero** mandate evidence to the 52-window gate.

That is a strictly negative trade: evidence-file noise for no gate progress. No backfill
was performed.

## Mitigating facts (recorded for completeness, not as grounds to force)

```
git diff --stat e7ed5375 233239a7 -- '*.py' '*.json' \
  ':(exclude)artifacts' ':(exclude)production_data' ':(exclude)research-inbox'
```

So the model code that produced the 07-27 snapshot is byte-identical to the code at
`233239a7`, and 07-27's close was settled before the run (pre-market 07-28), meaning the
prices were PIT-clean. The provenance mismatch is real but carries no data defect.

**This does not justify forcing the capture.** The gate's purpose is to guarantee that a
LIVE window came from a single uninterrupted invocation — a property that was genuinely
violated here. Asserting eligibility on the strength of "but nothing actually changed"
would substitute this session's judgement for the control, which is the failure mode
`feedback_no_governance_theater_evidence` exists to prevent.

production wrapper capture HEAD once at start and pass that value through to step [6],
so a mid-run HEAD move is detected and reported as an operator error rather than
